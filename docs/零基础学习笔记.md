## 第 0 章　先认识"计算机这台机器"

在谈 Java 之前，必须先知道**计算机物理上是什么**。否则后面全是空中楼阁。

### 0.1 CPU：一堆会开关的电闸

**CPU**（`CPU = 中央处理器，一台机器里的"大脑"）本质上是**几十亿个晶体管**（`晶体管 = 一个能用电压控制的微型开关`）拼成的电路。

- 每个晶体管只有两种状态：**开（有电）** 或 **关（没电）**。
- 开/关，我们用 `1` 和 `0` 来表示。所以 CPU 从头到尾只能"看懂" `0` 和 `1`。

你看到的一切——文字、图片、视频、程序——物理上**都是 `0` 和 `1`（高低电压）**。

### 0.2 指令：CPU 只会干极少几件事

CPU 能干的动作非常少，每一"件"叫一条**指令**（`指令 = CPU 能执行的一个最小动作`），比如：

- 把一个数字从内存搬到 CPU 内部（读）
- 把两个数字相加
- 把一个数字写回内存
- 跳转到某一行代码去执行

这些指令在 CPU 里也是**用 `0` 和 `1` 编码**的。比如在 x86 架构（`架构 = 一种 CPU 的设计标准`）里，`B8 01 00 00 00` 这串字节，意思是"把数字 1 放进某个寄存器"。

这种 CPU 直接认识的二进制指令，叫**机器码**（`机器码 = CPU 唯一能执行的二进制指令`）。

### 0.3 寄存器：CPU 手边的小格子

CPU 内部有几十个极小的存储格子，叫**寄存器**（`寄存器 = CPU 内部的高速小格子，一次只存一个数字`）。它快得离谱，因为就在 CPU 内部、离计算电路几纳米远。

几个重要的（记名字就行）：

| 寄存器 | 干啥 |
|---|---|
| **PC / RIP**（程序计数器）| 存"**下一条要执行的指令的内存地址**" |
| **RSP**（栈指针）| 指向**栈顶**（见第 2 章）|
| **RBP**（基址指针）| 指向当前函数的栈帧底部 |
| **RAX/RBX/RCX/RDX** | 通用格子，放要算的数 |

### 0.4 一条指令是怎么"执行"的：取指-译码-执行

CPU 每时每刻在做一个无限循环，叫**取指-译码-执行**（`取指=拿指令、译码=看懂它、执行=动手`）：

1. **取指**：看 PC 寄存器里的地址，去内存把那条指令读进来。
2. **译码**：看懂这条指令是"加法"还是"读内存"。
3. **执行**：真的去做，比如让加法电路把两个数加起来。
4. PC 加一，指向下一条，回到第 1 步。

CPU 有个**时钟**（`时钟 = 每秒震几亿次的节拍器`），每震一下推着这个循环往前走。你听到的"主频 3.0GHz"就是每秒震 30 亿下。

### 0.5 内存条：一排编号的小格子

**内存**（`内存 = 内存条 RAM，一排按地址编号的格子，断电数据就消失`）物理上是一长条电路，上面有几十亿个小格子，每个格子存 8 个 `0/1`，也就是 **1 个字节**（`字节 = 8 个 0/1`）。

- 每个格子有一个**地址**（`地址 = 格子的编号，从 0 开始数`）。
- CPU 读写内存，就是"报一个地址 → 内存条把那个格子的内容送回来"。
- 一格 = 1 字节。一个 int 占 4 格（4 字节），一个 long 占 8 格。

### 0.6 内存有多慢：存储层级

关键事实：**CPU 快，内存慢**。CPU 每纳秒能干好几次运算，但去内存条读一次数据要等几十纳秒——这中间 CPU 只能干等。所以中间加了几层"缓存"：

```
寄存器(最快, 0.几纳秒) → L1缓存 → L2缓存 → L3缓存 → 内存条(几十纳秒) → 硬盘(最慢, 毫秒级)
```

**缓存**（`缓存 = 把常用的数据抄一份放到离 CPU 更近的地方`）就是"抄近道"。后面讲数据库时你会再次遇到这个词，原理一模一样。

### 0.7 进程和虚拟内存

你双击运行一个程序，操作系统会创建一个**进程**（`进程 = 一个正在运行的程序，操作系统给它单独划了一块"领地"`）。

重点来了：每个进程都以为**自己独占一整块巨大的内存**，从地址 0 到几十亿。其实这是假的，叫**虚拟内存**（`虚拟内存 = 操作系统给每个进程画的一张"假地图"，每个进程都以为整片内存都是自己的`）。

真实情况：只有一小部分虚拟地址真的对应着物理内存条上的格子。有一张表（叫**页表**）记录"虚拟地址 1000 ↔ 物理地址 5亿"这种对应关系。CPU 里有个硬件 **MMU**（`MMU = 内存管理单元，专门负责把虚拟地址翻译成物理地址`）在每次读写时自动查表翻译。

> 这一层你现在不用记细节，只需记住一件事：**你程序里所有的"地址"，都是虚拟地址，不是内存条上的真实位置。** 翻译由 MMU 硬件自动完成，程序自己根本不知道真实位置在哪。

## 第 1 章　Java 到底是怎么被"翻译"成电信号的

你问"Java 的翻译官是什么，怎么翻译的"。这一整章就回答这个。

### 1.1 结论先说

**JVM**（`JVM = Java 虚拟机，一个用 C/C++ 写出来的普通程序`）不是一个"人"，而是一个**软件**。它的工作流程是：

```
你写的 Hello.java（人能读的文字）
      │  ① 编译（javac）
      ▼
Hello.class（字节码，一种"中间语言"，不是机器码）
      │  ② JVM 读取它
      ▼
JVM 把字节码翻译成"当前这台机器"的机器码
      │  ③ CPU 执行机器码
      ▼
变成电信号，真正跑起来
```

关键点：**CPU 只认识机器码，而机器码跟 CPU 架构绑定**（x86 的机器码在 ARM 手机上跑不了）。Java 的办法是**中间插一层字节码**，让"你的代码"和"具体机器"解耦。

### 1.2 什么是字节码

**字节码**（`字节码 = 一种给"虚拟机器"执行的中间指令，长得像机器码但不是`）是 `.class` 文件里的内容。

看个例子。你写：

```java
int add(int a, int b) { return a + b; }
```

编译成字节码后，大概是这几条（人看的助记形式，真实是二进制）：

```
iload_1      // 把参数 a 读进来
iload_2      // 把参数 b 读进来
iadd         // 相加
ireturn      // 返回结果
```

注意：这是给 **JVM 这台"假想的机器"** 执行的指令，不是给 CPU 的。真正的 CPU 看不懂 `iadd` 这种指令，只有 JVM 看得懂。

### 1.3 JVM 怎么"翻译"：两种方式

JVM 把字节码变成机器码，有两条路：

**方式一：解释执行（像人一句句念）**

JVM 内部有一个"解释器"，它做一个循环，逻辑就是：

```
while (还有下一条字节码) {
    读一条字节码（比如 iadd）
    去调用一段已经写好的机器码（C 语言写的"加法"实现）
    执行它
}
```

相当于：不把整本书翻译成英文，而是**拿一句念一句、念一句翻一句**。简单、启动快，但慢——每条指令都要"查一下该怎么办"。

**方式二：JIT 即时编译（把热点整段翻译好再跑）**

**JIT**（`JIT = 即时编译器，JVM 的一部分，把频繁执行的代码整段翻译成机器码`）会发现："这个 `add` 方法被调用了十万次了，是热点！"于是它把 `add` 这个方法**一次性完整翻译成机器码**，存进内存里一块叫"代码缓存"的地方，下次直接执行机器码，不再逐条解释。

相当于：发现某段话反复出现，就**整段翻译成英文并抄下来贴墙上**，以后照着念。

现代 JVM（HotSpot）**两个都用**（叫"混合模式"）：先解释执行快速启动，跑一会儿发现热点就 JIT 编译。还有"分层编译"：先用一个快的编译器（C1）粗翻译，真热了再用慢但优化狠的编译器（C2）重新翻译。

### 1.4 物理层面到底发生了什么

把整条链放平：

1. 你的 `.java` 是**硬盘上的文字文件**（一堆字节）。
2. `javac` 是另一个程序，读这个文件，输出 `.class` 文件（也是硬盘上的字节，但内容是字节码）。
3. 你运行 `java Hello`，操作系统启动一个进程，把 **JVM 这个程序**（本身是机器码）加载进内存，让 CPU 执行 JVM。
4. JVM 在内存里：读 `.class` 字节码 → 类加载器把类结构加载进内存 → 解释器/JIT 把字节码翻译成机器码 → 这些机器码被放进内存 → CPU 的 PC 寄存器指向它 → 取指-译码-执行，变成电信号跑起来。
5. 翻译出来的机器码，本质上和 JVM 自己（C 写的）一样，都是一串 `0/1`，CPU 用同样的方式执行。

> 一句话：**"翻译官"不是魔法，就是一个正在被 CPU 执行的软件（JVM），它把字节码翻译成 CPU 的母语（机器码），再交给 CPU 执行。**

### 1.5 为什么非要中间插一层字节码

因为**不同机器的机器码不一样**：x86 台式机、ARM 手机、不同操作系统，机器码都不同。如果 Java 直接编译成机器码，你得给每种机器各编一份。

有了字节码，你的 `.class` **只编译一次，哪都能跑**——只要那台机器上装了对应版本的 JVM（JVM 负责翻译成当地机器码）。这就是 Java 的口号 "Write Once, Run Anywhere"（写一次，到处跑）的物理含义。

## 第 2 章　堆和栈：内存条上的真实布局

你问"堆和栈到底是什么"。它们是**进程虚拟内存里两块用途不同的区域**。

### 2.1 一个进程的内存长什么样

操作系统给进程一块虚拟内存，大致分成几段（从低地址到高地址）：

```
低地址 ──────────────────────────────── 高地址
[代码段][数据段][ 堆 →  ...  ← 栈 ]
```

- **代码段**：你程序翻译出来的机器码就放这（只读）。
- **数据段**：全局变量、常量。
- **堆**：动态分配的对象，**往上长**。
- **栈**：函数调用的局部变量，**往下长**（x86 上）。

### 2.2 栈：一块用"指针"管理的内存

**栈**（`栈 = 一块连续内存，用栈指针 RSP 管理，专门放函数调用的局部变量`）的物理操作极简单：

- 有个寄存器 **RSP**（栈指针）指着"栈顶"。
- **要分配空间** = 把 RSP 往下挪一格（一条减法指令）。**释放空间** = 把 RSP 往上挪回来（一条加法指令）。
- 因为就是"挪一个数字"，所以**快得离谱**，纳秒级。

### 2.3 函数调用 = 压栈；返回 = 弹栈

每次调用一个函数，就在栈上"压"一个**栈帧**（`栈帧 = 一次函数调用在栈上占的那块地方，装着参数、局部变量、返回地址`）：

```java
void f() {
    int x = 1;      // x 就存在 f 的栈帧里
    int y = 2;      // y 也在 f 的栈帧里
    g();            // 调用 g：在栈上再压一个 g 的栈帧
}                   // f 返回：把 f 的栈帧弹掉，x、y 随之消失
```

物理上调用 `g()` 干了这几件事：

1. 把"f 里下一行代码的地址"（返回地址）压进栈。
2. 把 g 的参数压进栈。
3. 把 RSP 往下挪，给 g 的局部变量腾地方。
4. 跳转到 g 的代码执行。

g 执行完返回时：

1. RSP 往上挪（把 g 的栈帧整个"扔掉"）。
2. 从栈里弹出返回地址，跳回 f 继续。

**为什么局部变量"用完就没了"？** 因为它的物理存在就是"RSP 下面那段内存"，函数一返回，RSP 挪走，那段内存下次就会被别人覆盖——不是被擦除，是被**重新分配覆盖**。

### 2.4 栈的局限：为什么不能太大

- 栈大小**有限**（JVM 默认每个线程约 1MB）。
- 递归太深会把它用完，就报你熟悉的 **StackOverflowError**（栈溢出）——物理上就是 RSP 一路往下戳，戳穿了操作系统给它划的那块栈内存。

### 2.5 堆：动态分配的大仓库

**堆**（`堆 = 一块大内存区域，用 malloc/new 动态分配，放所有 new 出来的对象`）跟栈的区别：

| | 栈 | 堆 |
|---|---|---|
| 分配方式 | 挪一下 RSP 指针，O(1) | 要找空闲块，可能触发系统调用，慢 |
| 释放 | 函数返回自动弹掉 | 靠**垃圾回收**（GC）自动回收 |
| 大小 | 小（约 1MB/线程）| 大（可到几个 GB）|
| 放什么 | 局部变量、基本类型、引用 | `new` 出来的对象 |

堆的分配为什么慢？因为要**找空闲块**：内存里东一块西一块被占用，需要维护一个"空闲链表"，从里面挑一块合适的。用久了还会产生**碎片**（`碎片 = 小块空闲内存东一块西一块，拼不出一整块大的`）。

### 2.6 垃圾回收（GC）：堆的清洁工

堆上的对象没人再用时，谁去删？**垃圾回收器（GC）**。

基本思路（**标记-清除**）：

1. **标记**：从"根"（栈上的引用、寄存器里的引用等）出发，沿着引用一路找，凡是被找到的对象都打个"活着"的标记。
2. **清除**：没被打标记的对象 = 没人引用 = 垃圾，回收它占的内存。

现代 JVM 还分了**代**（新生代/老年代）：因为绝大多数对象"生下来很快就死"，所以把新对象放一块（新生代），经常快速回收；活得久的才搬去老年代，不常扫。这能大幅提高回收效率。

> 你项目里"内存泄漏"（`内存泄漏 = 对象没人用却一直不被回收，内存越占越多`）的本质：某个"根"一直引用着本该释放的对象，导致 GC 永远标记它为"活着"。

## 第 3 章　对象、引用、值传递的物理真相

### 3.1 一个对象在内存里的真实样子

`new User()` 之后，堆上出现**一段连续内存**，布局大致是：

```
┌────────────────────────────┐
│ 对象头（mark word）         │  ← 存哈希值、GC 年龄、锁信息
├────────────────────────────┤
│ 类型指针（klass pointer）    │  ← 指向"这个对象是哪个类"的元信息
├────────────────────────────┤
│ 字段1（如 name）            │
│ 字段2（如 age）             │
└────────────────────────────┘
```

- **对象头**：JVM 自己塞进去的管理信息（哈希码、垃圾回收年龄、锁状态）。
- **类型指针**：指向这个类在"元空间"（`元空间 = JVM 存"类本身的结构信息"的地方`）里的元数据。
- **字段**：你定义的 `name`、`age` 等，按顺序排。

### 3.2 引用里存的到底是什么

```java
User u = new User();
```

- 栈上有一个变量 `u`，占 8 字节（64 位机器）。
- 这 8 字节里存的**就是一个数字**：堆上那个 User 对象的内存地址（虚拟地址）。
- 你写 `u.name`，物理上是：CPU 取出 `u` 里的地址 → 用这个地址去内存读对象头 → 跳过对象头 → 读到 name 字段。

**引用，就是一个存了地址的 64 位整数。**（JVM 还有个优化叫"压缩指针"，在堆不大的时候用 32 位存地址，省内存，细节不用管。）

### 3.3 值传递的物理：就是"拷贝"

```java
void f(int x) { x = 100; }
void g(User u) { u.name = "改了"; }
```

- `f(a)`：把 `a` 的值（一个数字）**复制**到栈上 `f` 的栈帧里给 `x` 用。CPU 干的是一条 **MOV**（搬数据）指令。改 `x` 改的是那份拷贝，原来的 `a` 在别的栈帧里，没动。
- `g(user)`：把 `user` 里的**地址数字**复制一份传给 `u`。现在有两个变量（`user` 和 `u`）存着同一个地址。所以 `u.name = "改了"` 是顺着这个地址找到同一个对象去改——`user.name` 自然也变了。

**这就是"传引用"的真相：传的不是对象，是对象地址这个数字的拷贝。**

（补充：如果 g 里 `u = new User()`，是把 `u` 这个栈变量里的地址数字换成新对象的地址，`user` 里还是老地址，所以外面的 `user` 不变。）

## 第 4 章　可变 vs 不可变：String 底层是什么

### 4.1 String 的底层：一个 final 数组

Java 9 之后，`String` 内部就俩字段（简化版）：

```java
public final class String {
    private final byte[] value;   // 真正存字符的地方
    private final byte coder;     // 标记编码方式
}
```

- 字符其实存在一个**字节数组** `byte[] value` 里。
- `value` 是 `final` 的——**一旦指向某个数组，永远不能再指向别的数组**。
- 更关键的是：String 的**所有方法**（`toUpperCase`、`substring`、`trim`…）都**不去改这个数组**，而是 new 一个新 String 返回。

所以 "abc".toUpperCase() 物理上是：读原来的 `byte[]` → 算出大写的结果 → **new 一个新的 byte[]** → 放进新 String。原来的数组原封不动。这就是"不可变"的物理含义：**存数据的那个数组从没人去改它。**

### 4.2 字符串常量池：堆里的一块哈希表

JVM 的**堆**里专门有一块区域叫**字符串常量池**，物理上就是一个**哈希表**（`哈希表 = 一个能根据"指纹"快速查找的容器`）。

- 你写 `String a = "abc"` 这个**字面量**（`字面量 = 直接写在代码里的值`）时，JVM 去常量池查：有没有 "abc"？有就直接把地址给 a，没有就 new 一个放进去。
- 所以 `String a = "abc"; String b = "abc";` 里，**a 和 b 存的是同一个地址**，物理上只有一个数组，省内存。

这也是为什么 String 必须不可变：如果它能改，a 改了 b 也跟着变，共享就出乱子了。

### 4.3 为什么不可变就"线程安全"

**线程**（`线程 = 一个独立向前推进的执行流程`）可以简单地理解为"同时有好几个栈、各自在跑"。

如果 String 可被改，两个线程同时改同一个 `byte[]`，就会互相踩（一个写了一半另一个读）。因为它不可变——**谁都不能改那个数组，只能读**——所以天然安全，随便多少个线程共享都不用加锁。

### 4.4 BigDecimal 底层

`BigDecimal` 内部（简化）存了：

```java
private final BigInteger intVal;   // 数字本身（用大整数存，精度无限）
private final int scale;           // 小数点后几位
```

比如 `12.34` 存成"整数 1234" + "scale = 2"。它不可变，所以算一次产生一个新 BigDecimal。这就是它能精确表示金额的原因：它**不是用浮点数的二进制近似**，而是用"整数 + 小数点位置"精确表示。

（`double` 之所以会 `0.1 + 0.2 != 0.3`，是因为 0.1 在二进制里是无限循环小数，存不下，只能近似。物理上 CPU 里的浮点单元用固定的二进制格式存小数，天生有误差。BigDecimal 绕开了这套，用整数算。）

## 第 5 章　面向对象：对象在内存里长什么样

### 5.1 对象就是一段内存

第 3 章说过，对象 = 对象头 + 类型指针 + 字段。这里补一个关键：**对象的方法代码，不存进每个对象里**。

方法代码只存一份，放在**代码段/元空间**。对象里只存**数据**（字段）+ 一个"我是哪个类"的指针。

### 5.2 多态在物理上是怎么实现的：虚表（vtable）

这是理解面向对象的物理关键。

```java
Animal a = new Dog();
a.speak();   // 为什么知道要调 Dog 的 speak，而不是 Animal 的？
```

物理过程：

1. `a` 是个引用，指向堆上的 Dog 对象。
2. 对象头里的**类型指针**指向 Dog 类的元数据。
3. Dog 类的元数据里有一张表，叫**虚表（vtable）**，`虚表 = 一个"方法名 → 方法机器码地址"的对应表`，里面写的是"speak → Dog.speak 的机器码地址"。
4. 调用 `a.speak()` 时，CPU 顺着：对象 → 类型指针 → vtable → 找到 speak 对应的机器码地址 → 跳过去执行。

**所以"多态"不是魔法，而是"运行时顺着对象的类型指针查表，找到实际方法地址再跳转"。** 这就是为什么同一个 `a.speak()`，指向 Dog 就调 Dog 的，指向 Cat 就调 Cat 的——因为它们的类型指针指向不同的 vtable。

### 5.3 接口是什么

接口在 Java 里就是"只声明方法名、不写实现"的约定。实现类必须把方法补全。物理上接口没太多额外内存，主要影响 vtable 怎么查（接口调用多一次查接口表），细节你暂时不用管。

## 第 6 章　IoC / 容器 / 反射：Spring 的物理实现

前面讲了那么多底，现在终于能真正说清 Spring 的"容器"物理上是什么。

### 6.1 反射：JVM 提供的"运行时照镜子"能力

**反射**（`反射 = JVM 让你在程序运行时查看"某个类有哪些字段、方法、注解"，甚至动态创建对象、调用方法`）是 Spring 的地基。

它为什么能做到？因为 JVM 加载类时，把**类的结构信息**（字段名、方法名、方法机器码地址、注解……）都存进了内存（**元空间**）。反射就是给你一套 API 去读这些元信息。

```java
Class<?> c = User.class;              // 拿到 User 类的"说明书"
Field f = c.getDeclaredField("name"); // 读到 name 字段
Method m = c.getMethod("setName", String.class);  // 读到 setName 方法
Object obj = c.getConstructor().newInstance();    // 不看代码直接 new 一个
m.invoke(obj, "张三");                // 不看代码直接调用 setName("张三")
```

`newInstance()` 和 `invoke()` 物理上就是：JVM 去元空间找到构造方法/方法的机器码地址，然后跳过去执行——**绕过了"写代码时就得知道类名"的限制，运行时拿到名字就能干活**。

### 6.2 注解的物理：类文件里存的一段"标签数据"

你写的 `@Service`，编译后会作为**元数据**写进 `.class` 文件。JVM 加载类时把它读进元空间。反射里可以这样读：

```java
c.isAnnotationPresent(Service.class)   // 问：这个类有没有 @Service 标签？
```

所以注解物理上就是：**存在类元数据里的一段"标签"信息，反射能读到它。**

### 6.3 Spring 容器，物理上就是一个哈希表

这是全章最重要的结论：

> **Spring 容器（ApplicationContext）的物理本质，就是一个大的哈希表（Map）：`"bean 名字" → "对象实例"`。**

启动 Spring 时，它做的事（物理上）：

1. **扫描**：去代码里找所有带 `@Component`/`@Service`/`@Controller` 等标签的类（本质是扫描 `.class` 文件 + 反射读注解）。
2. **实例化**：用反射 `newInstance()` 把这些类 new 出来。
3. **依赖注入**：发现某个对象的字段/构造参数还缺依赖，用反射去找、new、塞进去（给字段赋值或传构造参数）。
4. **存表**：把造好的对象放进那个哈希表，键是名字（如 "bidServiceImpl"），值是对象。
5. 你 `@Autowired` 一个字段时，Spring 用反射找到字段类型，去哈希表里把对应对象取出来，塞进字段。

**默认这些对象是单例**（`单例 = 哈希表里这个名字只存一个对象，大家共享同一个`）。

### 6.4 所以 IoC 和 DI 的物理含义是

- **IoC（控制反转）**：以前"创建对象"这条指令在你的代码里（你写 `new UserService()`）；现在被挪到了**Spring 的启动流程**里（它替你 new）。控制权从你的代码手里，交到了 Spring 手里。
- **DI（依赖注入）**：Spring 用反射，把哈希表里的依赖对象，自动写进你的字段/构造参数里。

一句话物理总结：**容器 = 一张哈希表 + 一套"扫描注解→反射创建→反射注入"的启动流程。**

## 第 7 章　HTTP：一段文字是怎么变成电信号跑出去的

### 7.1 HTTP 本身只是"一段文字"

你在代码里发的 HTTP 请求，本质上就是**一段纯文本**（几个字节拼成的字符串）：

```
POST /api/tenders HTTP/1.1
Host: localhost:8080
Content-Type: application/json

{"project_name":"水泵","quantity":10}
```

就这么简单：一行"方法 + 路径"，几行头部，一个空行，然后是正文（JSON）。**HTTP 协议（`协议 = 双方约好的通信格式`）就规定了这段文字该怎么排版。**

### 7.2 但这段文字不能直接"飞"过去：要一层层打包

网络通信是**分层**的（从上到下，每层给上一层的包裹加一个"信封"）：

| 层 | 干什么 | 加的信封 |
|---|---|---|
| 应用层（HTTP）| 定义"请求/响应"文字格式 | 上面那段文字 |
| 传输层（TCP）| 保证**可靠送达**（不丢、不乱序）| 加"端口号、序号"等 |
| 网络层（IP）| 负责**找路**（路由）| 加"源 IP、目标 IP" |
| 链路层（以太网）| 负责**同一条网线/局域网内**传送 | 加"MAC 地址" |
| 物理层 | 把 `0/1` 变成**电信号/光信号** | 实际的电脉冲 |

物理层上，你那段文字最终变成**网线上的一串电压跳变**（或光纤里的一串明暗），这就是"电信号"。

### 7.3 TCP 的"可靠"靠什么：三次握手

HTTP 建在 TCP 上。TCP 为了保证双方都准备好了，发数据前要**三次握手**（`握手 = 双方确认能互相通信`）：

```
客户端 ── SYN ──▶ 服务器        (1) 我想连你
客户端 ◀─ SYN+ACK ── 服务器     (2) 好的，我也准备好了
客户端 ── ACK ──▶ 服务器        (3) 收到，开始传数据
```

之后你的数据被**切成一个个小包**（`数据包 = 被切碎的、带信封的数据块`）发出去，每个包带序号，接收方按序号拼回来、缺了就让对方重发。这就是"可靠"。

### 7.4 套接字和端口：怎么找到你后台那个程序

- 一台服务器上跑着很多程序，操作系统用**端口号**（`端口 = 一个数字，用来区分同一台机器上的不同程序`）区分。你后端监听 **8080**，MySQL 监听 **3306**。
- **套接字（Socket）**（`套接字 = 操作系统提供的一个"通信口"，程序通过它收发数据`）就是你程序手里的那个"电话听筒"。Tomcat 在 8080 端口上创建套接字监听，浏览器连过来，双方就通过各自的套接字读写数据。

### 7.5 JSON 序列化的物理

`JSON`（`JSON = 一种 {名字:值} 的文字格式`）就是"把对象变成一段文字"。

你 `return new Result<>(data)`，Spring 用 Jackson（一个库）走**序列化**（`序列化 = 把对象里的字段读出来，拼成一段文字`）：反射读对象每个字段 → 转成字符串 → 拼成 JSON 文字 → 作为 HTTP 正文发出去。浏览器收到后**反序列化**（`反序列化 = 把文字解析回对象`），变回前端能用的对象。

> 所以整条链是：**你的 Java 对象 → Jackson 反射读字段 → 拼成 JSON 文字 → TCP 切包 → IP 路由 → 以太网帧 → 电信号 → 对方网卡 → 一路反向解包 → 浏览器拿到 JSON。**

## 第 8 章　数据库：数据在磁盘上怎么存、索引为什么快、事务靠什么

### 8.1 数据在磁盘上：页

数据库（如 MySQL 的 InnoDB 引擎）不把数据当"一行行"存，而是按**页**（`页 = 磁盘上一块固定大小的数据块，默认 16KB`）读写。

- 磁盘很慢（毫秒级），而且**连续读一大块和读一小块差不多快**，所以一次就搬一页（16KB），里面装几百行。
- 表里的行，就密密麻麻塞在这些页里，通过一个叫 **B+ 树**的结构组织起来。

### 8.2 为什么"索引"能加速：B+ 树让树变矮

先想：没有索引，查 `WHERE id = 5000` 要**把整张表一页页翻一遍**（全表扫描），100 万行要读很多次磁盘，极慢。

**索引**（`索引 = 给某一列建一个"排好序的目录结构"`）解决的就是"少读几次磁盘"。

物理结构：给 `id` 列建索引，就是把所有 id **排好序**，组织成一棵 **B+ 树**（`B+ 树 = 一种多叉的、保持有序、且矮的树`）。它的特点是**每个节点能存几百上千个 id**，所以：

- 树**非常矮**：100 万行数据，树高也就 3~4 层。
- 查一个 id = **从树根往下走 3~4 层**，每走一层读一页（一次磁盘 IO），总共读 3~4 次磁盘就定位到数据。
- 对比全表扫描可能要读几万页。

**索引快的物理本质：把"读几万页"变成"读 3~4 页"。**

### 8.3 索引是什么做的（回到你项目）

建索引是写 SQL，不是 Java。你项目 `database/schema.sql` 里：

```sql
KEY idx_tender_status (status),      -- 普通索引：给 status 列建目录，按它查更快
UNIQUE KEY uk_bid_manufacturer_project (manufacturer_id, tender_project_id)
```

- `KEY idx_xxx (列名)`：普通索引，物理上就是给那列建一棵 B+ 树。
- `UNIQUE KEY`：**唯一约束**，除了建索引，还强制"这列/这组列不能重复"。物理上插入时会去索引里查"有没有一样的"，有就拒绝。这就是防重复投标的物理兜底。

### 8.4 缓冲池：把磁盘搬到内存

磁盘慢，所以 InnoDB 有个**缓冲池**（`缓冲池 = 数据库把常用的页缓存到内存里`）。查过的页先放内存，下次再查直接命中内存，不碰磁盘。这跟你电脑 CPU 的缓存、第 0 章讲的存储层级，**原理完全一样**：常用数据抄到更近的地方。

### 8.5 事务靠什么实现：日志 + 锁

事务的四个特性（ACID），物理上各靠什么撑起来：

| 特性 | 靠什么 | 物理大白话 |
|---|---|---|
| **原子性**（要么全做要么全不做）| **undo log**（撤销日志）| 每改一行前，先把"旧值"记下来；要回滚就照旧值改回去 |
| **持久性**（提交了就永久保存）| **redo log**（重做日志）| 每次修改先写日志（顺序写，快），再改数据页；就算突然断电，重启后照着 redo log 把没落盘的修改补上 |
| **隔离性**（并发互不干扰）| **锁 + MVCC** | 加锁让冲突的操作排队；或用 MVCC 给每个事务一个"快照"，各看各的 |
| **一致性** | 由上面三个共同保证 | 数据始终从"合法状态"到"合法状态" |

**MVCC**（`MVCC = 多版本并发控制，让每个事务看到数据的一个"历史版本"，读不加锁`）：物理上是数据行里存着"版本号/事务号"，读的时候按你的事务号，去取你该看到的那一版，而不是最新的。这样"读"和"写"不用互相锁死，并发性能好。

### 8.6 你项目里的"事务"落地

`@Transactional` 物理上是：Spring 的**代理对象**（`代理 = 你的 Service 外面包了一层替身`）在方法开始前，向数据库发"开始事务"；方法正常结束发"提交（commit）"；中途抛异常发"回滚（rollback）"。

回滚时，数据库就靠上面说的 **undo log** 把已经改的行一条条改回旧值。这就是为什么你注册时"插了 users 又插 manufacturers"，如果第二步失败，第一步插进去的那行会被数据库用 undo log 撤掉——**不会出现脏数据**（`脏数据 = 不该存在的不完整数据`）。

## 第 9 章　回到本项目：每个黑话的物理落地

把前面所有底，落到你的项目里。每个词一句话点破它的**物理本质**：

| 黑话 | 物理本质 |
|---|---|
| **分层架构** | 把"接请求/业务/查库"拆成几个类，本质是让调用链清晰、互不依赖（内存里就是对象之间互相调用的引用关系）|
| **统一返回** | 所有接口返回同一个"文字格式" `{code,message,data}`，前端按固定格式解析 |
| **全局异常** | 一个 `@RestControllerAdvice` 用反射/拦截统一接住异常对象，转成统一文字返回 |
| **JWT 鉴权** | 登录发一张"带签名的字符串"（token），签名 = 用密钥对内容算出的**哈希**（`哈希 = 把任意数据算成固定长度指纹`）；之后每次请求验签名识别身份，服务器不用存会话 |
| **权限/越权** | 认证=验你是谁；授权=`@PreAuthorize` 检查你的角色；越权防护=Service 层查"这条数据的归属字段是不是你的"，不是就抛 403 |
| **逻辑删除** | 不物理删除行，只把 `deleted` 字段从 0 改成 1（一个 UPDATE），查询时自动过滤 `deleted=1` 的行 |
| **索引** | 给列建 B+ 树目录，把"读几万页"变成"读 3~4 页" |
| **防重复投标** | 应用层先查一次 + 数据库 `UNIQUE KEY` 在插入时用索引查重强制拦截（物理兜底）|
| **事务** | Spring 代理发 begin/commit/rollback，数据库用 undo/redo log 保证原子与持久 |

## 第 10 章　面试话术 + 学习路线

### 10.1 能镇住面试官的几句"底层话术"

- **JVM 是什么**："JVM 是个软件，把平台无关的字节码翻译成本地机器码；解释器逐条执行，热点方法用 JIT 整段编译成机器码缓存起来，所以能做到'一次编译到处运行'。"

- **堆和栈**："栈是一块用栈指针管理的连续内存，函数调用压栈帧、返回弹掉，O(1) 分配所以快；堆是动态分配的大区域，对象都在这，由 GC 标记-清除回收。"

- **引用和值传递**："Java 只有值传递。引用本质上是个存了对象地址的 64 位整数；传对象是把地址拷贝一份传进去。"

- **String 不可变**："String 内部是 final 的 byte[]，所有方法都返回新对象不改原数组，所以天然线程安全、能进常量池共享。"

- **多态**："对象头有类型指针指向类元数据，方法调用走 vtable 虚表查实际方法地址，所以能动态分发。"

- **Spring 容器/IoC**："容器物理上就是一张 bean 名字到实例的哈希表；启动时扫描注解、反射实例化、反射注入，把'创建对象的控制权'从业务代码反转到了框架。"

- **索引为什么快**："B+ 树矮、每节点存很多键，把查找从'全表扫几万页'降到'读 3~4 页'。"

- **事务**："@Transactional 靠代理发 begin/commit/rollback；原子性靠 undo log 回滚，持久性靠 redo log 重做，隔离性靠锁 + MVCC。"

### 10.3 学懂的标准

不是背名词，而是**能把一件事从"代码"讲到"电信号/内存/磁盘"**。比如别人问"什么是引用"，你能说出"是个存了对象地址的 64 位整数，解引用就是 CPU 拿这个地址去内存读"——就真的懂了。
